# 官方 CLI 等待配置与完整回归

2026-11-05，使用官方 `timeouts.settle=0`，同一 MCP 实例连续完成 Character、Date、五字段 Record＋Build、四步 AE。共 381.175 秒，409 个节点全部成功，0 识别轮次重试、0 节点失败、0 动作失败；全部保存、关闭并经 DBX 验收。没有删除业务检查、修改安装中的 CLI 源码或改变 Maa 的延迟配置。

## 原因与生效方式

实际安装的官方 CLI 为 1.65.0-alpha-2026-10-30。其 run-code 调用 `waitForCompletion`，默认 settle 500ms；Tab.waitForTimeout 实际通过 `page.evaluate` 在页面里调用 setTimeout，后台页面的计时调度会影响实际等待。本机隐藏页面空请求中位数约 954ms，原画布编码约 50ms，不能将这整段时间算作截图编码。

该配置在 CLI daemon 启动时加载，单条命令加参数不能更改已有 daemon 的配置。项目提供 [官方配置文件](../../playwright-cli.config.json)。通过官方已绑定浏览器入口创建新的 CLI 会话，复用已授权的 Chrome，无需再建立扩展授权：

```text
node <配置中的 cli_script> -s=psauto-fast attach psauto-discovery --config=<本项目绝对路径>/psauto/playwright-cli.config.json
```

执行目录使用配置中的 cli_workdir，CLI 安装必须与原会话相同。`psauto-discovery` 是本机已绑定浏览器的名称；`psauto-fast` 是新的调用会话。前者仍提供底层浏览器，需保持运行；本项目结束调用只停止自己的常驻客户端。

本机先尝试了新扩展连接；后台 Windows 会话与 Chrome 桌面会话不同，该尝试未完成，期间没有开始业务操作。随后改用上述已绑定入口，约 2 秒连接成功。临时计划任务已移除，后续无需依赖它们。

项目连接配置明确指定 `cli_session:psauto-fast`、`cli_settle_ms:0`、`cli_persistent_client:true`。常驻客户端启动时通过官方 config-print 读取实际 settle 值；值不符则拒绝提交浏览器动作，不偷偷回退。每个任务 timings.json 写入预期及实际值，避免错误地拿 500ms 会话做 0ms 测试。`cli_settle_ms:null` 仅保留旧配置兼容，不启用此项校验。

已启动的 MCP 服务不会自动重新导入 Python 模块或读取修改后的 config.json，需重新启动该 MCP 连接。本轮完整测试明确新建了一个加载最终代码和配置的服务实例，并在其中连续执行四次调用。
