# 合并浏览器检查，减少 CLI 调用内的查询往返

2026-11-05，相对 `66196b3`，合并 Playwright CLI 适配器的浏览器查询，并修复真实回归发现的 Record 字段 ROI 和 Build 后关闭目标。每次请求仍重新检查连接、尺寸、图层、可见性和必要的键盘焦点；截图仍先排空 Guacamole 已接收的绘图队列。状态每次重读，保存、Build 和空白台成功判决保留；业务 JSON 的两处改动和失败样本在下文单列。

## 原因与测量边界

GM_EXP_REC 比此前 GM_OPT_REC 慢约 60 秒，其中原生执行阶段增加约 56 秒，主要体现在截图和输入调用，而不是新增节点或识别重试。两次发生于不同时间，旧日志只有完整 CLI 调用耗时，不能进一步认定是 CPU、CDP、网络或 Chrome 后台调度中的哪一项导致。

本轮开始时，在同一现场页面连续只读测量 12 次：页面可见、1920×897、DPR=1，原图仍为 1920×1080。CLI 空请求中位数 14.3ms，截图 CLI 124.4ms，Python 解码 43.7ms；截图 JS 整体 107.5ms，其中连接检查 33.5ms、flush 调用 22.0ms、inspect/取图调用 51.0ms。浏览器内部的画布检查与编码约 17ms。具体记录见 [改造前现场分解](roundtrips/prechange_live_probe.json)。各项中位数不保证相加等于总中位数。

这次没有重现此前约 1–2 秒的偶发长尾，且页面可见性与历史隐藏页面不同，不能据此断言长尾已解决。分解数据支持另一个确定的成本：旧截图前置检查跨越 count、连接读取、flush、inspect 多次浏览器查询；普通输入还单独读取焦点。当前一次查询的固定成本比 DOM 内执行检查本身明显。

## 实现与保护

通过单次 `locator.evaluateAll` 顺序执行连接检查、必要的 Guacamole flush、原有 `_INSPECT` 和尺寸/焦点检查。依旧使用原函数和全部条件；连接与画布状态每次请求重读，不保存旧快照。缺显示、缺组件/API、关闭隧道、错误尺寸、异常图层或失焦均停止。

flush 的 5 秒上限仍在浏览器页面外执行，避免隐藏页面计时器节流影响超时。合并后的回调只检查、刷新绘图队列和读图；实际按键、点击或粘贴在成功返回之后执行，超时后的迟到回调不能发送输入。key_up 的异常释放路径保留。点击的缩放映射、顶层/iframe 遮挡检查及 swipe 逐步尺寸检查保留原实现。兼容的 browser 刷新模式继续完成浏览器截图/抽屉动画，并在刷新后重查状态。

Maa 原生节点事件和已有 `timings.json` 继续保留。既有 transport 行现在额外记录 body、browser_roundtrip、browser_validation、browser_flush、browser_inspect 分项。Controller 截图还记录 decode_ms；elapsed_ms 继续只表示 CLI 往返，不包含 decode，保持旧统计口径。body 包含 roundtrip，roundtrip 包含浏览器内部阶段，不能将这些嵌套时段直接相加。计时行不保存代码、密码、URL 或图片正文。

## 真实调用暴露的区域问题

首个新 MCP 创建 `GM_RPC_REC` 在保存前停止：137 个节点中 136 完成，5 轮识别重试、1 个节点失败、0 动作失败，返回 workspace_ready=false / next_operation_allowed=false。失败位置是 `R_Attr3_Bind` 之后寻找第四行字段的 `R_AttrFocus`；实际 OCR 把蓝色选中单元左侧边框读成引号，得到 `"EFFDT`，严格整行规则正确拒绝通过。完整失败证据为 `out/objects/20261105_175023_339465`，不计完整成功或有效业务提速样本。

初始空表格记录的 Field Name 锚点为 `[659,290,65,24]`，旧 offset `[-5,20,100,400]` 得到 `[654,310,165,424]`，包含左边框。改为 `[5,20,90,400]` 后得到 `[664,310,155,424]`：左界向右 10px，右界保持，仍识别完整字段名。没有放宽名称正则或增加固定等待。原失败 PNG 已作为 [回归夹具](../../tests/fixtures/vision/record_selected_effdt_prefix.png) 保留。

离线复现必须使用任务最初记录的锚点：若对已经填好字段的截图重新定位表头，OCR 框会变动，会掩盖旧 ROI 的问题。原生测试固定该真实锚点，旧 crop 稳定失败，新 crop 对五个字段均通过，错误字段名仍拒绝，均不发送输入；13 项原生识图回归通过。此结果证明旧 crop 在该选中状态有缺口，不能凭本次失败认定是 transport 合并造成。

主控通过独立临时 Pipeline 只关闭并丢弃本次创建的 Record14 未保存草稿，识别确认空白台后，启动新 MCP 实例从头创建 `GM_RPC_REC2`。这属于明确检查后的人工开发重测，不是服务自动重放，也不是接着未完成对象凑完整成功。新的完整结果独立记录。

第二次 `GM_RPC_REC2` 已保存且 Build 通过，但最终关闭没有完成，MCP 返回 partial / saved=true / built=true / workspace_ready=false / next_operation_allowed=false，完整调用 180.22 秒，不能计为完整成功。原本 `R_BuildFocusEditor` 点击 OCR 标题框中的随机点；该框包含窗口图标，本次实际点击 `[636,268]` 打开了 MDI 系统菜单，后续 Ctrl+F4 没有关闭窗口。失败证据为 `out/objects/20261105_180031_075459`。

Build 后改为 `R_BuildCloseSaved`：同一次 And 识别同时要求完整对象名和既有 close 图片，`box_index=1` 指向按钮，直接 Click，然后确认空白台。将“点击标题→Ctrl+F4”合并为一次明确的关闭点击，保留全部身份、按钮和空白台检查；Build 路径因此从 208 变为 207 节点。非 Build 的保存关闭路径保持。

新增原生测试使用真实 Build 完成帧，正确对象时只点击关闭按钮框内一次；相似的错误对象名和缺关闭图时均不点击。14 项原生识图回归通过。主控先以独立临时 Pipeline 识别本对象的系统菜单、Esc 退出菜单，再执行新关闭节点，确认空白台；这是失败后的人工开发收尾，不追改第二次 MCP 的 partial 结果。随后用新服务实例从头创建 `GM_RPC_REC3`，作为最终版本的完整验证。

最终 `GM_RPC_REC3` 完整调用 173.22 秒，207 节点全部完成，保存/Build/关闭/空白台通过，证据 complete 且允许下一操作；DBX 也确认五字段属性、HRAPP、3 个 VALID 索引和 0 行。4 次额外扫描均在等待对话框出现，没有重发输入或动作失败。原生任务 144.187 秒，导出 27.449 秒；整体与更早约 170 秒的较快样本接近，不能只拿较慢的 230 秒样本宣称稳定的整体提速。全部失败、partial 和成功分开记录，详见 [完整截图、逐节点计时与 DBX](../images/acceptance-roundtrips-20261105/README.md)。

随后同一新 MCP 实例连续创建 GM_RPC_F1 和引用它的 GM_RPC_REC4＋Build，分别 48.89 / 175.53 秒、40 / 207 节点，均保存关闭、证据 complete 且允许下一操作；Record4 零扫描重试、零节点/动作失败，DBX 也通过。两次最终版本 Record 都已实际通过新关闭节点，前两次开发失败仍分开保留。

新分项还捕获到一次 2232.81ms 的 click：其中 browser_roundtrip 为 1065ms，浏览器内部检查合计约 1.6ms。这说明该次大段等待发生在查询往返或调度，不能解释为画布编码/OCR；也不能进一步断言是哪层 CPU/网络/Chrome 调度造成。剪贴板输入仍约 2 秒，其中保留原有 1000ms 同步等待和浏览器动画完成检查。后续可据此继续细分等待，当前没有删除保护或固定等待来制造提速结果。
