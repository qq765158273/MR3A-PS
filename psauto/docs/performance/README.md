# GM_MCP_REC4 为什么耗时约 16 分钟

结论：主要开销在 Playwright CLI 的截图和输入传输，以及过细的节点拆分。识别耗时占约 3%，本轮没有操作失败或重试循环。当前实现需要优化，不能用“识图慢”解释这次耗时。

数据来自完整成功的 `out/objects/20261104_183010_506938/`，逐条解析 Maa 的 `events.json`、`report.json`，并对照 `debug/maafw.log` 的控制器回调时间。原始日志及截图保留在本机。已提交 [226 个节点逐步耗时 CSV](record4_nodes.csv) 和 [汇总 JSON](record4_summary.json)，均由实际日志生成。

## 互不重叠的耗时分解

| 项目 | 秒 | 占 Pipeline 时间 |
| --- | ---: | ---: |
| 截图及下一轮识别前的准备 | 532.227 | 58.8% |
| 控制器执行输入动作 | 238.439 | 26.3% |
| 动作前后等待 | 102.461 | 11.3% |
| 全部识别，含 OCR、模板及候选分支 | 28.591 | 3.2% |
| 引擎起始阶段 | 4.078 | 0.5% |
| Pipeline 合计 | **905.796** | 100% |

从后台进程启动到最终 MCP 结果文件落盘为 971.59 秒，另有约 65.8 秒在上述事件跨度之外，包含启动、导出截图和事件、最后截图及返回。不能把这部分都算作业务界面等待。

原生日志另记录了 226 次 `screencap` 回调，累计约 533.3 秒、中位数 2.742 秒。此项与表中的截图准备时间属于重叠口径，边界略有不同，不能再次相加。

## 节点数量与失败情况

- 实际是 **226 个完成节点**，不是 900 多步；平均每节点约 4 秒。
- 226 轮下一节点扫描，246 次候选识别，226 次规则通过，226 次动作成功；动作失败为 0。每轮扫描中没有同一候选被重复尝试。
- 20 次 `Node.Recognition.Failed` 均为候选分支未命中。例如先看是否已经勾选，未命中后走“未勾选则点击”；它们不是 20 次操作失败。
- 5 个 `R_AttrDone` 使用 `inverse:true`，检查属性窗口已消失，因此原始 `hit:false` 正是通过条件。CSV 同时记录原始命中值、反向规则和最终规则是否通过，避免把这类日志误读成失败。
- 89 个节点为 `DoNothing`，65 个节点的识别算法是 `DirectHit`。两组有交叉，不能相加。即使节点只传递控制或执行按键，目前引擎仍会调用截图。

按阶段分配相邻扫描间隔：插入字段约 252 秒，字段属性约 350 秒，查重约 82 秒，Build 设置和完成检查约 76 秒。数据库建表并没有持续 15 分钟。

## 为什么“每步延迟 1 秒”并不等于 1 秒一步

当前一个节点通常包含：取新截图、识别、默认 200ms 前延迟、调用输入、默认 200ms 后延迟。`rate_limit:1000` 是扫描循环的间隔下限，不是整个节点的时间预算；截图本身已花 1.4–3.3 秒。把它调小，并不能消除 CLI 调用时间。`timeout` 是等待上限，也不是每步必定睡满的时长。

日志中的动作中位数：点击约 1.662 秒，单个按键约 1.720 秒，剪贴板输入约 3.718 秒。控制器会为每次请求新建临时 JS 文件，再启动一次 Node/CLI 客户端进程，调用已经存在的浏览器会话。浏览器没有每次重开，但客户端调用有重复开销。

例如第一次打开字段属性的 Ctrl+Enter 被拆成三步：

| 节点 | 动作 | 包含下一轮截图准备的分配时间 |
| --- | --- | ---: |
| R_AttrControl | 按住 Ctrl | 5.000 秒 |
| R_AttrEnter | 按 Enter | 5.000 秒 |
| R_AttrControlUp | 松开 Ctrl | 4.063 秒 |

一个快捷键就分配了约 **14 秒**。中间两次截图没有承担业务状态判决。这说明动作粒度和传输开销需要一起处理。

## 对当前浏览器的只读补测

2026-11-04，复用当前 CLI 会话，未创建或修改业务对象：

| 补测 | 三次结果 |
| --- | --- |
| `run-code` 直接返回 true，无页面操作 | 2001、2004、1998ms |
| 当前原始画布截图 | 1999、2001、1999ms |
| 激活目标标签后，空命令 | 2000、2000、2000ms |
| 激活目标标签后，原始画布截图 | 2005、1996、2000ms |

前后 `document.visibilityState` 均为 `hidden`，只激活标签没有解决问题，原始画布仍为 1920×1080。请求浏览器等待 500ms 的一次内部计时，实测约 1371ms；标签激活后约 1360ms。三次样本只证明本机当前状态，不能当成另一环境的保证。

已安装 Playwright CLI 0.1.23 的官方实现还会在 `run-code` 后执行 `waitForCompletion`，默认 settle 为 500ms；它通过页面内 `setTimeout` 等待。隐藏页面会放大该等待。当前 `run-code` 命令也不接受临时的 `--timeout-settle` 参数，不能仅在每条命令后加一个开关解决。历史运行没有记录每次客户端启动与浏览器内部等待的独立跨度，因此不能把本次空命令的 2 秒原样分摊到之前的每次调用。

## 优化顺序

1. **优先处理 CLI 调用和后台等待。** 测清客户端启动、会话通信、默认 settle、刷新浏览器帧、原图读取和解码各自的时间。验证 CLI 支持的会话配置及浏览器后台策略；目标是让空命令和截图明显低于当前约 2 秒。复用官方会话和客户端能力，Maa/MR3A 的识别引擎继续使用原实现。
2. **减少不承担界面判决的控制节点。** 连续快捷键、修饰键按下/松开等应尽量一次发送，避免中间截图；具体组合键支持先做隔离验证。勾选后的状态、编辑器身份、保存成功、Build 和空白台等检查继续保留。
3. **按节点调整延迟。** 当前全部节点都有默认 200ms 前延迟，普通动作后多为 200ms；`DoNothing` 识别已成立后的延迟可先评估减少。只减这些等待，理论上也仅省约 102 秒，仍无法把 15 分钟降到合理目标。
4. **去掉证据的重复导出。** 当前同时导出节点图与识别事件图，共 473 张 PNG、约 17.1MB；按 SHA-256 比较，只有 107 种不同文件内容，366 个文件与其他文件完全相同。相同帧可共用文件引用，保留每步日志和失败样本；还可验证无损 PNG 的压缩级别。导出不能继续占约一分钟。

上述内容保留优化前的诊断口径。后续已实现客户端常驻、Record 组合键、延迟调整和证据去重，并用相同五字段场景完整创建 GM_MCP_REC7：总耗时从 971.590 秒降为 524.384 秒，DBX 验收通过。实现、校准失败和完整对照见 [优化记录](optimization.md)。

CSV 的 `next_scan_prepare_s` 计入前一行，表示该行完成后到下一轮识别开始的间隔；包含下一次取图及准备，不应称为该行识别算法时间。CSV 各行时间加引擎起始 4.078 秒，与 905.796 秒总跨度相等。
