2026-11-05，仍使用原 MR3A / Maa Pipeline、识别器和原生事件。此次针对 Field / AE 合并同一状态上的重复截图检查，并验证隐藏 Chrome 下的 Guacamole 绘图刷新。运行时没有 AI 决策，代码正文只经剪贴板输入及保存反馈，不做 OCR 回读。

保留旧节点作为开发入口，正式入口已绕过重复节点；不会因为 JSON 中仍有定义而执行它们。保存、关闭和空白台检查均保持。`failed_node` 改为取原生 `Node.PipelineNode.Failed` 的位置；此前截图失败可能错误显示为更早的查重候选未命中，现在不再使用候选 miss 作失败位置。

## 截图为什么约需 1 秒

五次连续只读原图请求的分项记录见 [原始测量 JSON](audit_capture_breakdown.json)：

| 阶段 | 实测范围 |
| --- | ---: |
| 排空 Guacamole 已接收绘图队列，含浏览器调用 | 18–21 ms |
| 原始画布读取、PNG 编码及该次浏览器调用 | 47–50 ms |
| 整个截图 JS 函数 | 98–103 ms |
| Python 解码 | 44–70 ms |
| 完整 CLI 请求，尚未计 Python 解码 | 932–1001 ms |

因此不能把 `scan_prepare_ms` 全部解释为截图编码。它是 Maa 原生节点开始到识别开始之间的跨度，包含截图、传输和下一轮准备。实际官方 CLI `browser_run_code_unsafe` 会调用 `waitForCompletion`，其 `timeouts.settle` 默认 500ms；完整请求还包含 daemon、协议及结果返回开销。测量没有将剩余约 0.8–0.9 秒进一步全部归入某一项。

原始画布保持 1920×1080，避免将浏览器显示缩放后的像素交给 OCR；这项读取本身不是主要瓶颈。Guacamole 的 1920×1088 分配缓冲仍只裁掉末尾 8 行。

## 隐藏页面刷新与失败边界

此前 `GM_AE_BASE` 有两次业务开始前截图失败，另一次部分保存到 Step02 类型后，隐藏 Chrome 的 `page.screenshot` 再次超时；该对象不计完整成功，也不是有效的前后性能对照。后来只关闭已保存窗口，空白台识别通过。收尾时一次 Ctrl+F4 未关闭窗口，识别已保存状态后点击关闭图标成功；未重放整次创建。

CLI 默认 `canvas_refresh_mode:guacamole`。截图前通过现有 Guacamole `client.getDisplay().flush(callback)` 排空**已经收到**的绘图队列，5 秒上限，再读取原始 canvas。它不请求远端生成新帧，也不能证明网络没有卡住；下一步仍必须识别到期望状态。缺组件、缺 API、分辨率不符、刷新抛错/超时或过程中断线都停止，不静默回退或使用旧图继续。

显式 `browser` 模式保留原浏览器截图刷新，供兼容诊断和本地测试；生产 Guacamole 模式不自动切换。剪贴板抽屉是网页遮挡，仍使用浏览器截图完成动画，再确认抽屉隐藏、尺寸和焦点；该只读截图最多重试一次，各 5 秒。Ctrl+V 前再次确认连接。点击、粘贴、保存、Build 均不因截图失败而重放。
