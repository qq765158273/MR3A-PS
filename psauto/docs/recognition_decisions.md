# PSIDE 卡点、等待与下一步判决

本表按实际出现过的卡点及关键操作边界维护。识别和分支由 Maa 原生 Pipeline 执行；Python 不看图决定下一步。图像匹配指 TemplateMatch，文字识别指 OCR；状态颜色使用 Maa 的 ColorMatch。

普通控件图片以 0.85 作为候选阈值。共同边框、相似编号、禁用文字都可能超过该阈值，所以还要检查具体差异和页面归属。对象名、字段名、表空间等变化内容保留必要的局部 OCR。代码正文不做 OCR，也不在保存后重新打开核对。

## 延迟和重试的具体含义

2026-11-05 合并同一画面的重复检查后，四步 AE 的活路径为 124 个节点，保存前 Dirty 直接执行 Ctrl+S，保存反馈、PeopleCode 编译反馈及空白台仍保留。Field 类型和长度标签合为一个 And 再点击，连续按键使用原生列表。Guacamole 模式截图前只排空已收到绘图队列；缺组件/API、超时和断线即停。剪贴板最后粘贴前重查连接，浏览器抽屉遮挡检查不省略。完整验收与取舍见 [Pipeline 复核](performance/pipeline_audit.md)。

`post_delay` 是动作后的初始缓冲，不能证明动作完成。真正的完成依据是 `next` 的识别条件。普通按键多为 100–300ms，输入约 300–500ms，打开编辑器 1000ms，Build 3000ms；剪贴板传输还会等网页抽屉离场并恢复远程键盘焦点。

Maa 的 `rate_limit` 默认 1000ms，是识别循环的最短间隔；实际还包含 Playwright CLI 截图和识别耗时。`timeout` 控制**当前节点等待 next 候选**的时长，不应只把超时写在目标检查节点上。已据此把代码保存释放按键后的等待设为 30 秒、Build Execute 后的等待设为 60 秒。用原生 Maa 做的隔离探针验证了这个语义，以及 max_hit=1 只允许一次恢复、两次尝试后停止。

识别失败后的重复截图不等于重复执行动作。当前仅为“重新选择 AE 动作行、重新打开菜单”配置一次幂等重试；它发生在粘贴和保存之前，并要求仍处于正确的已保存 AE 窗口。点击打开代码编辑器后，身份未确认就停止。粘贴、保存、Build、创建结果不明均不自动重放。

性能优化只将 Record 的节点前延迟及已通过识别的 DoNothing 后延迟设为 0，并合并输入适配器中的组合键。输入后缓冲、状态检查和 Save/Build 上限保留。任务超时或常驻客户端异常仍停止后续输入，不通过切回单次客户端来重放。实际延迟分布与 46% 的完整耗时变化见 [性能对照](performance/optimization.md)。

失败保留 request、Pipeline override、report、events、节点截图和失败节点。CLI 超时可能仍有未完成动作时，连接标为不确定并停止后续命令；已部分保存但未关闭时返回 partial 或 workspace_ready=false。不能把分段修正后的完成算成原完整 MCP 调用成功。

2026-11-04 实测曾出现 tunnel=CLOSED、剪贴板禁用，而客户端文字状态仍为 Connected，原始画布停在旧编辑器。适配器现拒绝这种状态；原生集成测试覆盖旧画布不被使用、点击/粘贴被拒绝、已按下 Ctrl 得到释放，以及 OPEN 时不误用不可靠的旧 connected 布尔字段。实际在空白操作台主动断开后，MCP 已自动走重连、验证活动 RDP 和 HRDEV，再开始 Record3 的首次创建；业务结果仍以完整调用终点为准。

已观察结果、样本范围和反例见 [识别方法对比](recognition_comparison.md)，完整调用与 dbx 状态见 [验收记录](acceptance.md)。AE3 两步和 AE4 四步完整调用已通过上述选择、菜单和保存检查；一次重试的次数边界另由隔离的原生 Maa 探针验证。当前记录仍不能证明长期稳定或跨 DPI 可用。
